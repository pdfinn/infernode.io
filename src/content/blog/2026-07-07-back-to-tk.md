When you fork a system that has gone a decade without maintenance, you have to keep deciding what to repair and what to replace. In March we decided to replace Inferno®'s Tk. We added `module/widget.m`, a native Limbo widget toolkit with buttons, listboxes, text fields, scrollbars and status bars drawn directly with `Draw`. It gave the desktop the flat, single-accent look we wanted, and Tk ended up disabled on the platforms we ship.

This week we reversed that decision. [PR #350](https://github.com/infernode-os/infernode/pull/350), a series of nearly a hundred commits, moved every GUI app back to the classic Inferno Tk and deleted the native toolkit: 1442 lines of `appl/lib/widget.b`, 484 lines of interface, and its two test suites. This chapter covers why we went back, and what Tk had been hiding while it sat unused on a 64-bit system.

## Why go back

The native toolkit ended up as a second, smaller Tk that every app had to work around. Each app hand-rolled its layout and drawing with manual `Draw` calls, kept its own focus and key handling, and rebuilt features Tk already has. Most of all, it lacked a real text widget. When we scoped the remaining migrations we confirmed that Tk's text widget is a complete editing surface, so the editor and shell could drop their custom buffer models and keep only a thin 9P bridge. Tk also brings string commands that a test harness can replay. We kept one thing from the native toolkit, its look, and applied it to Tk.

The migration guide we wrote along the way is [docs/TK-MIGRATION.md](https://github.com/infernode-os/infernode/blob/master/docs/TK-MIGRATION.md).

## Bringing the engine back

On Linux, Tk was not just unused but compiled out. `lib tk` and `mod tk` were commented out of the emulator config, so `load Tk Tk->PATH` returned "module not built-in". Turning them back on was straightforward. Making Tk testable without a display took more work. The headless emulator's `attachscreen` used to return nil, so nothing Draw-based could run there. It now gives `devdraw` an in-memory framebuffer. Pixels can still be read through `Display.writeimage`, which means a Tk window can be rendered and checked in CI.

`libinterp/tk.c` still carried scaffolding from an earlier attempt that had stalled. It included per-command hex dumps to stderr and `fixconfigurecoords()`, which rewrote `. configure -x N -y N` whenever the coordinates "looked garbage", blamed on "DIS VM stack frame corruption". That diagnosis was wrong. On our build `WORD` is pointer-sized, so Limbo `int`s, and therefore `Draw->Rect` coordinates, are 64-bit. The C-side `Limbo_Rect` (four `vlong`s) already matched the generated layout. The workaround was hiding correct values, so we removed it.

That episode taught us something about how we work. We develop with AI coding assistants. They make it cheap to try a fix, and a plausible explanation like "VM stack frame corruption" arrives just as cheaply. What resolved it was checking the claim against the running system. Reading `top.screenr` from Limbo on a live toplevel returned the correct `(0,0)-(1600,1024)`, and that settled it.

## The 64-bit colour bugs

Giving Tk the Brimstone palette (surface `#080808`, text `#cccccc`, accent `#e8553a`) exposed three bugs, all from 32-bit assumptions in C:

- **Macro precedence.** `RGB()` in `colrs.c` didn't parenthesise its arguments. With `HEXRGB`'s `(v>>16)&0xff` as input, `R<<24` parsed as `(v>>16) & (0xff<<24)`. That zeroed red and green, so `#CCCCCC` came out as `#0000CC`. The original colour table only worked because it passed bare literals.
- **Sign extension.** Colours are built as `(R<<24)|(G<<16)|(B<<8)|A` with `R` an `int`. When `R ≥ 0x80`, the shift produces a negative number, which sign-extends into the 64-bit `ulong`. Drawing survived because the draw layer only uses the low 32 bits. But `cget -background` returned `#ffffffffccccccff`, and the fast paths for pure white and black never matched.
- **Fill width.** `memfillcolor` built a 32-bit pixel pattern and filled with `memsetl`, which writes native 8-byte words on a 64-bit host. That zeroed every other pixel. On Brimstone's near-black surface the zeroed pixels were invisible. On the light Halo theme, every label background became a black checkerboard.

A fourth bug was more serious. `Buffer.rgba` in `libmemdraw` was a `ulong *`, so the same-channel alpha-blend fast path read, wrote and advanced 8 bytes per 4-byte pixel. Few paths reach it. The About box does, because Tk copies its alpha-channel logo through `tkreplimg`. The copy read about one scanline past the buffer, corrupted the free tree of the image memory pool, and crashed some time later in `poolfree`. That was the "About wedges the system" crash. The fix changed the type to `u32int *`, and we confirmed it with an ASan build.

All of these come from code written before 64-bit hosts were the norm, and none had been exercised this way before. This is what bit rot looks like up close. The code was not wrong when it was written. The machines around it changed.

## The app recipe

Every app now follows the same pattern. It creates a `tkclient` toplevel, builds its UI with `tk->cmd` strings, and receives app actions on a buffered channel:

```limbo
actch := chan[8] of string;
tk->namechan(top, actch, "act");
# button .b -command {send act save}
```

Tk handles focus, editing and press feedback. In order, we moved about, keyring, wallet, man, fractals, ftree, editor, shell, settings and the matrix display modules, then luciconv's inline dialogue buttons, and finally Charon. Once Charon no longer imported `widget.m`, we could delete the toolkit.

The migrations exposed some engine gaps and gotchas that apps had been papering over:

- **Named images did not update dependent widgets.** `tk->putimage` into a named bitmap never told the label displaying it, so a label created before its image was filled stayed blank at zero size. Apps had been re-issuing `configure -image` after every update. We added `tkimgchanged()` to `libtk`, which unblocked `wm/fractals`.
- **Menus were invisible everywhere.** Tk posts a menu by requesting a window on `top.wreq`, and none of the hand-rolled event loops read that channel. Menus were mapped and grabbed the mouse but had no window. In fractals, a right-click would select a menu entry you could not see and silently switch fractal sets. All nine apps now service `wreq`.
- **Widths are in pixels.** Inferno Tk's `-width` is in pixels, not characters as in Tcl/Tk. A label column sized as if in characters clips to a single glyph.

Brimstone in Tk is also flat. The palette pins every relief's light and dark shades to the border colour, and we rewrote the scrollbar and scale as flat blocks with no arrows or bevels. The palette is read from the active `lucitheme`, so the same apps appear in Halo when that theme is selected.

## Things the GUI shook loose

Running every app headless turned up two VM problems unrelated to Tk:

- Reading `/prog/<n>/status` for a JIT-compiled program called `msize()` on a pointer into the executable code arena. That tripped the allocator's validation while it held the pool lock, and the emulator then waited forever on the VM run token. `wm/task` froze the GUI as soon as it opened. The fix skips the code-size term for compiled modules, the same guard `freemod()` already used.
- Because that was the second whole-VM freeze in a short time, we added owner tracking for the run token and a watchdog. If processes are waiting and the owner hasn't changed for 30 seconds, the watchdog prints who holds the token, or "token LOST". A healthy system passes the token constantly, so an unchanged owner with waiters always means something is wrong.

## How it is tested

`tests/tk_test.b` runs in the standard runner on the in-memory display. It checks toplevel geometry, widget creation, the default palette (guarding against the macro bug), colour round-trips through `cget` (guarding against sign extension), key injection into entries, button invocation, listbox selection, check and radio variables, text editing, and dynamic images. For visual review, `tests/tkrender.b` replays a file of Tk commands onto a toplevel with no window manager and writes the image. `tools/tk-snapshot.sh` turns that into a PNG on the host. Because no event loop runs, a replay cannot hang the way spawning a full app could.

The merge added 15020 lines and deleted 21318.

## What we learned

The lesson is not that the native toolkit was a mistake. It established the look, and that carried over. The lesson is about what to keep. Tk was worth repairing because the repairs were finite and the result was the toolkit the rest of the system already expected. Several of those repairs, like the sign extension, the fill width and the alpha-blend overrun, would have affected anything that used those drawing paths, toolkit or not. Bringing old code back into use is how we find out what is wrong with it, and this was a large amount of it brought back at once.

What we gain for the agent work is a desktop built from commands that a test can replay and render without a screen. Veltro already drives apps such as man and ftree through their IPC files, so we need to be able to check what those apps show.
