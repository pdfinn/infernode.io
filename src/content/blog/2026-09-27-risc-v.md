Portability was one of Inferno®'s original promises. Dis is the same bytecode on every machine, so a program written once runs wherever the virtual machine does. That promise is only as good as the list of machines the VM actually runs on. When we forked, the list was a decade out of date. The upstream history already held a RISC-V toolchain, contributed by Richard Miller in 2020, but the tree had no emulator, JIT or kernel for RISC-V.

[#718](https://github.com/infernode-os/infernode/pull/718), merged on 26 September, ports InferNode to 64-bit RISC-V (RV64GC) in both of the ways it runs elsewhere. The hosted emulator runs on riscv64 Linux with its own Dis JIT. The native kernel runs on QEMU's RISC-V `virt` machine and on the Microchip PolarFire SoC, which is the chip on the BeagleV-Fire and the Icicle Kit.

This is also the clearest test so far of the other experiment behind this project: whether a small team working with AI coding assistants can close a gap of years. A new JIT and a new kernel architecture are the kind of work that used to take a long time. Speed is not the measure, though. What counts is whether the result can be trusted, and for a port we trust only what the tests show. That is why so much of this post is about test harnesses.

One caveat applies to the whole post: **everything here has run under QEMU only**. No RISC-V board has booted it yet. The port's [README](https://github.com/infernode-os/infernode/blob/master/os/riscv64/README.md) ends with a first-boot checklist for the BeagleV-Fire for that reason.

## Hosted: a JIT ported from arm64

`build-linux-riscv64.sh` builds the emulator either natively or cross from amd64 or arm64, and it runs under `qemu-riscv64` without hardware. The machine-specific parts are small:

- `_tas` is an `amoswap.w.aqrl`.
- `segflush` uses the `riscv_flush_icache` syscall, which flushes on all harts. A local `fence.i` would flush only the current hart.
- `fpuctl.h` is backed by the real `fcsr`.

`libinterp/comp-riscv64.c` is a port of the arm64 JIT. Three RISC-V details shaped it:

- **Branch reach.** Branches to Dis instructions and macros are relaxed across three passes. A B-type branch reaches ±4 KiB and a `JAL` ±1 MiB; anything farther uses `auipc`+`jalr`. Addresses of C functions come from a per-module pool through `auipc`+`ld`.
- **Division never traps.** RISC-V returns a defined result on division by zero, so the JIT tests the divisor explicitly. Bounds, nil and zero-divide faults store `R.PC` and `R.FP` before raising, so that the right exception handler catches them.
- **Bounds are always checked.** The arm64 JIT emits its index checks only when `bflag` is set. `emu -b` is documented as on by default, but `bflag` starts at zero and nothing in the tree sets it, so honouring the flag would have compiled every index unchecked. The RISC-V JIT ignores `bflag` and checks every index, as the interpreter does.

The opcode suite `/dis/jittest.dis` passes 182 of 182 cases with `-c1`. The new `tests/jit_fault_test.b` covers zero divide, bounds and nil faults, plus unwinding to the correct handler. CI gained a `linux-riscv64-cross` job that cross-builds the emulator and runs these tests under `qemu-riscv64`, with both the JIT and the interpreter.

## Bare metal: `os/riscv64`

The native kernel compiles `os/port`, `os/ip` and the libraries from the same files the arm64 kernel uses. `os/riscv64` adds only what RISC-V needs: entry, traps, the SBI, the PLIC, `spl` and locks, a 16550 console and the process switch.

The kernel runs in S-mode under SBI firmware. Some choices worth noting:

- **`tp` holds the per-hart `Mach` pointer.** The psABI already reserves `tp`, so no compiler flag is needed. It is deliberately not restored on trap return, so a process that migrates sees its new hart's `Mach`.
- **Paging is off (`satp` Bare).** On RISC-V, cacheability and atomics come from the platform's memory attributes, so nothing requires paging. Sv39 protection is later work.
- **The timer uses SBI `set_timer`, not `Sstc`.** The PolarFire's U54 cores lack `Sstc`.
- **The kernel takes the Linux boot contract.** That means the hart id in `a0`, the device tree in `a1`, and a Linux `Image` header at the start of `l.S`. Whatever boots a Linux `Image` boots this kernel, including U-Boot's `booti`, and a generated `boot.scr` makes that unattended.

Two pieces of arm64 code turned out to have nothing ARM-specific in them, and they moved rather than being copied. The virtio-mmio transport, its block, network and input drivers, and the device-tree reader now live in `os/virtio`. The framebuffer, software cursor and text console now live in `os/fb`. [docs/BAREMETAL-BOARD-INTERFACE.md](https://github.com/infernode-os/infernode/blob/master/docs/BAREMETAL-BOARD-INTERFACE.md) already called for that: a third board should make the move rather than the copy.

On QEMU's `virt` machine (`os/riscvvirt`), the kernel runs four harts with the JIT on. It finds virtio network, block, keyboard and tablet devices. With a `ramfb` screen, `wm/logon` draws the graphical logon through `devdraw`, written in Limbo and compiled by the new JIT. The harness confirms the logon is on screen by taking a QMP screendump.

## The PolarFire SoC

`os/mpfs` needed no changes in `os/riscv64`. The board runs the kernel on its four U54 application harts, while hart 0, the E51 monitor core, stays with the firmware. Bringing the board up took these drivers:

- **SD card.** The Cadence SD4HC turned out to be a standard SDHCI register set 0x200 above Cadence's own registers. So it became another `SDio` under the card layer that the Raspberry Pi ports already used, and that interface moved from `os/bcm` to `os/port/sdio.h`. With the card mounted, `osinit` grows `/dis` and `/lib` from it and takes a writable `/usr`, just as on a Pi.
- **Ethernet.** The Cadence GEM became `#l/ether0`. It has two descriptor rings, and its PHY is driven over MDIO. Under QEMU, DHCP answers through it.
- **Entropy.** Random numbers come from the system controller's nonce service, a TRNG-seeded SP 800-90 DRBG reached through a mailbox. An all-zero answer counts as a failure. If the service is refused, the board falls back to its loud "no entropy source" path. QEMU's model refuses every service, so the harness checks that the refusal is reported. The success path needs real silicon.
- **eMMC.** The BeagleV-Fire's 16 GB eMMC sits on the same controller. The card layer, which spoke only SD, now falls back to MMC initialisation when nothing answers `ACMD41`. QEMU cannot attach an eMMC to the Icicle Kit's SD bus without a one-line patch, so CI also builds a patched QEMU 9.2.4 that can.

Two more changes prepare for a board we haven't been able to inspect. A U-Boot built with `CONFIG_SMP` sends every hart into the kernel at once. The BeagleV-Fire ships a vendor U-Boot whose configuration we don't know, so `l.S` now holds Linux's hart lottery. Every hart does an `amoadd` on a shared counter, and the winner boots. The losers stop themselves through SBI HSM and are started properly later. And if the firmware's console is not MMUART0, the kernel moves its console to whichever UART `/chosen/stdout-path` names, so that the board doesn't go silent after "Starting kernel".

The 38 checks on `virt` and 31 on the PolarFire model pass on the distribution's QEMU 8.2, and all 73 pass on the patched QEMU 9.2.4.

## What the port found in code we already had

A new architecture can expose old bugs, and this one exposed two.

The first was a nil module pointer. Diagnostics added during the Pi 3 work read `R.M->compiled` after checking `R.M` against `H`. A Prog whose module is not linked yet has `R.M` nil, so the read was of address `0x10`. The arm64 kernel maps page zero, so the read returned junk and nothing noticed. The RISC-V kernel addresses memory physically with nothing at `0x10`, and the read faulted on the first instruction of the first Dis program.

The second bug was in every JIT. A compiled module returns through its `ret` macro. When the module's `Modlink` is about to lose its last reference, that macro calls C `OP(ret)` from the module's own code. `OP(ret)` destroyed the `Modlink`, which unloaded the module and, since an earlier fix to JIT slab management, also unmapped its code. The C call then returned into unmapped memory. A server that unloads modules while calls into them are running does exactly this. On riscv64 it showed up as crashes in the `pqauth`, `interop` and `cipher_matrix` tests.

The fix keeps such a `Modlink` in `retpending` until control is back in C, and the garbage collector's root set marks it so that a sweep cannot free it first. The new `tests/jit_unload_test.b` reproduces the crash deterministically. Without the fix it fails on amd64, arm64 and riscv64; with the fix it passes on all three. The same crashes disappeared from `matrix_test`, which had shown 3 per run on amd64, 6 on arm64 and 3 on riscv64.

## What we learned

The port's most valuable output was not RISC-V support. It was the two bugs in code we already had. The RISC-V kernel addresses memory physically, with nothing mapped at page zero, and that made a latent nil read fatal on its first instruction. Running the whole test suite on a third JIT showed that a crash we had been seeing intermittently was a lifetime bug shared by all of them. A new target works like a new reviewer that doesn't share your assumptions. That holds for code written with assistants as much as for code written by hand, and maybe more so.
