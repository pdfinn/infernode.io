We forked Inferno® to build a place where software agents could run with exactly the authority we give them, through per-process namespaces, and no more. That only matters if the agents can do something useful, and almost everything useful is behind HTTPS. Here the size of the gap we took on became very concrete. The tree we inherited carries `appl/lib/crypt/ssl3.b`, an SSL 3.0 implementation whose version table stops at `SSL_VERSION_3_0`. No public server will negotiate that today, and nor should it.

Closing gaps like this one is half of what InferNode is for. The other half is an experiment. We are a small group working with AI coding assistants, and we want to find out whether that combination can bring a system with a decade of bit rot up to date in months rather than years. TLS was a good early test, because cryptography is where fast and plausible is most dangerous.

## Fast, and honest about it

The work merged on 17 February [with the `arm64-jit-rewrite` branch](https://github.com/infernode-os/infernode/pull/15). It kept the split Inferno has always used. Arithmetic that must be fast and constant-time lives in C in `libsec`, gets a binding in the `Keyring` module, and is called from Limbo. The protocol state machine, record layer, key schedule and certificate handling are Limbo, in [`appl/lib/crypt/tls.b`](https://github.com/infernode-os/infernode/blob/master/appl/lib/crypt/tls.b).

The [first commit](https://github.com/infernode-os/infernode/commit/e047f2b100558ac236d2c025a87986f4659525e4) arrived early in the morning with more than 4,000 lines: AES-GCM, AES-CTR, ChaCha20, Poly1305, the combined AEAD, X25519, HMAC over SHA-256/384/512, a 1,600-line Limbo TLS module, and HTTPS wired into the agent's HTTP tool. That is the productivity an assistant gives you. The commit message is the part we would point other teams at: "crypto primitives not yet validated against RFC test vectors. P-256 is a stub. Certificate name verification is TODO." Code that looks finished is not finished, and the message says so. The rest of the day was spent deleting those sentences one at a time, each against an oracle we did not write.

## The vectors

The [next commit](https://github.com/infernode-os/infernode/commit/333852184c63c46b6f846b19d6bc90d7eca4a938) checked every primitive against published vectors: RFC 4231 for HMAC, NIST SP 800-38D for GCM, RFC 8439 for ChaCha20-Poly1305, RFC 7748 for X25519. Six bugs fell out:

- GCM: a spurious `bitrev8`, though GCM already uses the reflected bit convention
- GCM: GHASH nibble order reversed (it must be LSB-first for a right-shift Horner evaluation)
- GCM: the GHASH reduction table mapping bits to the wrong constants
- Poly1305: `r` clamping masks written for 28-bit limbs in code that uses 26-bit limbs
- X25519: the conditional subtraction in `fcontract` with its polarity inverted
- X25519: two masks swapped in `fexpand`

None of these crashes anything. Each gives a cipher that decrypts its own output perfectly and interoperates with nobody, so a round-trip test passes. That is the first lesson of this chapter, and it will come up again: when code is cheap to produce, the scarce thing is a ground truth that did not come from the same place as the code.

[P-256](https://github.com/infernode-os/infernode/commit/77781b7828de8d3ba1b2c3118f55c202018717cd) replaced its stub with real field arithmetic, Jacobian point operations, a constant-time Montgomery ladder, and ECDSA on top of `libmp`. Three more bugs of the same kind were caught on the way. `fe_add` dropped the carry whenever a + b ≥ 2^256, roughly half of all additions. The schoolbook multiply overflowed its 128-bit accumulators. `mptobe` left-justified its output. The same commit added hostname verification against CN and SAN, verification of the TLS 1.2 ServerKeyExchange signature, and TLS 1.3 CertificateVerify with RSA-PSS. It also deleted a hard-coded `insecure=1` from the agent's HTTP tool and its `mc9p` client. Before that line went, neither checked anyone's certificate.

## The servers

Vectors test primitives. Only a real server tests a handshake. The [live suite](https://github.com/infernode-os/infernode/commit/4253a64a1ff54bac4b427f281d5ce8a2385946a2) handshakes with example.com and cloudflare.com and issues a GET. It found five protocol bugs:

- Servers send a plaintext ChangeCipherSpec in the middle of the encrypted handshake for middlebox compatibility (RFC 8446 §5), and we must skip it.
- Servers pack EncryptedExtensions, Certificate, CertificateVerify and Finished into one encrypted record, and we were reading one message per record.
- The transcript hash used to verify Finished and CertificateVerify must exclude the message being verified, so it has to be saved before that message is read.
- Application traffic secrets have to be derived before the client sends its own Finished.
- A `break` inside a `case`, meant to leave the enclosing loop, only left the `case`. That is a Limbo trap, and a Go one too. We rewrote the loop as `while` with a flag.

By evening, [X.509 handled ECDSA chains](https://github.com/infernode-os/infernode/commit/9d7f3f5ce29e2f72fc8cf96efd7e2f51c6924765). The 1990s ASN.1 parser learned UTF8String, which modern certificates use. A chain-reversal bug was fixed: `verify_certchain` reversed the chain twice. The [last commit](https://github.com/infernode-os/infernode/commit/b82099eaf48de56d8a7d1b604b2819a44c232a8f) added P-384 verification, a trust store of eight DER roots in `lib/certs/`, and a reusable HTTPS client, `module/webclient.m`. The live suite passes 4 of 4, including a rejected hostname mismatch. The crypto suite passes 13 of 13.

## One barrier

The same merge fixed something that had been costing us intermittent crashes on ARM64, and it is a good example of bit rot that is not really rot. Nobody wrote anything wrong: `unlock()` in `emu/port/lock.c` released the lock with a plain store, which is safe under x86's strong memory ordering. On ARM64's weakly ordered memory, stores inside the critical section can become visible after the store that releases the lock. The [fix](https://github.com/infernode-os/infernode/commit/98ce289561a0c7f1ef4189395113da6817d00b0e) uses `stlr`, store-release, as Linux's `arch_spin_unlock` does. Under heavy lock contention we went from 6 crashes in 20 runs to none in 40.

## Where this leaves us

TLS 1.2 is limited to ECDHE_RSA. The trust store is eight roots, not a system bundle. There is no revocation checking. Those are known and next. The more important result is about method. In one day we went from no modern TLS to a verified TLS 1.3 handshake against public servers. An assistant made the volume possible, and test vectors and real servers made it trustworthy. We intend to keep working that way: generate quickly, and never accept what was generated against a test written from the same understanding.
