We forked Inferno® on one premise: Plan 9's model is the right one for containing an AI agent. Every resource is a file, every process has its own namespace, and an agent cannot reach what is not in its namespace. [The escape room](/blog/the-escape-room/) is how we test that premise. A live model is told to get out of a Veltro namespace and recover canaries it was never granted. Since 2 September the harness has lived in [its own repository](https://github.com/infernode-os/infernode-escape-room) and pinned the exact InferNode revision it attacks.

We tagged 0.4.0 on 12 September, and the campaign kept running against it. [InferNode 0.4.1](https://github.com/infernode-os/infernode/releases/tag/v0.4.1), tagged on 17 September, is a security patch. It carries three containment fixes from what the campaign found in the days that followed, and a wallet change that operators need to know about.

## A claim we had to retract

0.4.0 finished our port of the Fourth Edition pathname stack ([#600](https://github.com/infernode-os/infernode/pull/600)). Its changelog said that Veltro's private `.veltro-ns` shadow tree, the scaffolding used to build an agent's namespace, was no longer visible from inside. Through `tools9p`, the server that gives an agent its tools, it was still visible.

The cause was ordering. `tools9p` restricted `/tmp/veltro/.ns` after it had already replaced the worker's `/tmp`, and doing so recreated `/tmp/.veltro-ns` inside the view the model could see. A single `list` showed the shadow tree, and concurrent calls exposed the names of live worker directories. [#619](https://github.com/infernode-os/infernode/pull/619) completes the shadow-backed restriction before the final `/tmp` replacement, and makes model-facing calls wait for the trusted startup manifest probe. The 0.4.1 changelog states plainly that the 0.4.0 entry was wrong.

The underlying mechanism was correct. The bug was in the order we used it in. A namespace is built one step at a time, and each step changes what the next one sees.

## `#e` is still `#e`

The second finding goes deeper into Inferno®. A Veltro tool worker gets a narrowed `/env`, with only allow-listed variables bound in, and runs under `NODEVS`, which stops it attaching new kernel devices by name. However, Inferno deliberately lets a process name its *own* environment device, `#e`, even after `NODEVS`. A worker that had inherited its launcher's environment group could therefore bypass the narrowed `/env` view by spelling it `#e`, and read the unfiltered original.

The `/env` restriction was a view over something the process could still reach another way. [#618](https://github.com/infernode-os/infernode/pull/618) fixes this at the root. Every tool worker now starts with `pctl(NEWENV)`, copies in only `VELTRO_SESSION`, and only then applies `NODEVS` and the namespace restriction. Its own `#e` now contains nothing worth reading. `appl/veltro/SECURITY.md` records the ordering and the reason for it, so nobody later "simplifies" `NEWENV` away because `/env` already looks restricted.

## A malformed stat, and a wallet setting

The third fix is in the emulator's C code ([#617](https://github.com/infernode-os/infernode/pull/617)). `statcheck` stepped through a 9P directory entry by a string length it took from the untrusted entry, without checking that length against the bytes actually returned. A malformed entry could make it read past its buffer and fault the emulator. Each entry is now checked against the remaining span before any field is decoded. A regression test runs it under ASan and UBSan against a guard page.

The wallet change is the same lesson from another direction: a policy setting that turned out to be a capability ([#627](https://github.com/infernode-os/infernode/pull/627)). The wallet's `requireapproval off` turned the same agent-visible files into immediate spending, without changing the agent's namespace or its `nsaudit` report. An auditor reading the namespace would see a proposal capability, while the agent actually held spending authority. In 0.4.1 every `pay` and x402 authorization needs trusted approval, and `requireapproval off` is rejected. Any future direct-spend authority must fail closed unless enforcement evidence is bound to the capability.

## Scoring the escape room honestly

Most of the escape room's own work in September went into its verdicts rather than its attacks. A model asked to escape will happily report that it escaped. It will also report that it was contained when it wasn't looking in the right place. Three changes in the harness this month address that:

- **Four axes, not one verdict.** Each result records execution and evidence, namespace configuration, machine-observed containment, and the model's own claim. The top-level verdict is derived from the first three. The model's verdict is kept as "hostile testimony" and marked verified, contradicted or unverified. The model cannot assign its own score.
- **Preflight before spend.** Before any request to the model, the harness boots every declared namespace in configuration-only mode and compares its live tools, paths, metadata and `nsaudit` report against the declared fixture. One unsafe or drifting cell rejects the whole campaign.
- **Fail on reported violations.** If the model reports an escape or a boundary violation, the result is treated as a security failure until the evidence says otherwise, not dismissed because no canary appeared.

None of this changes the claim a passing campaign is allowed to make, which stays as narrow as before: this build, this construction, this model, this prompt, these trials. What changed is how well the harness can tell a pass from something that only looks like one. The argument for why a namespace is the right boundary to test at all is in [our paper on namespace-bounded agents](PAPER_URL).

## What the findings have in common

None of these problems broke the Plan 9 model itself. Each was a place where our use of it did not match the model. A restriction applied in the wrong order. A view over a device the process could still name directly. A parser that trusted a length. A setting that changed authority without changing the namespace. That last case is the one we think about most: if the namespace is the capability, then anything that changes what an agent can do has to show up in its namespace, or the audit is not telling the truth.

The campaign continues against each new pinned build. The next one is harder to run, because it now refuses to start when the configuration it is about to attack doesn't match what was declared.
