InferNode began as an attempt to make Acme into an AI text editor. Acme SAC (Acme Stand Alone Complex), Caerwyn Jones's standalone packaging of Acme, showed how much an editor built from files and plain text could carry. We forked Acme, the fork became Xenith, and Veltro, our agent, first lived in Xenith windows, with a REPL in its own window. That was the right place to start. Acme's model, in which every window is a set of files and any text can be a command, is a natural fit for an agent that works by reading and writing files.

By late February it was clear that we had far more than an editor. Inferno® ran 64-bit on ARM64 and AMD64 with JIT compilers. Veltro could plan, call tools, spawn sub-agents in narrower namespaces, and speak and listen. The namespace model that contains the agent was working. But to use any of it you had to know Acme: three mouse buttons, middle-click to execute, the tag line, a command language that rewards years of practice. That suits the Plan 9 people we hoped to reach, and it shuts out almost everyone else. If we wanted a broader audience, the interface had to be simpler. You should be able to talk to the agent, see what it produces, and see what it can reach, without learning a text editor's grammar first.

That interface is Lucia. In the code it is called Lucifer, so the programs are `lucifer`, `luciuisrv` and `lucibridge` and the themes live in `/lib/lucifer/`. Today we merged it to master as [PR #41](https://github.com/infernode-os/infernode/pull/41), and the macOS app now [launches it by default](https://github.com/infernode-os/infernode/commit/5cef428a7f2e32b3d155772e1a263814174fb7b4) in place of Xenith.

## Three zones

Lucia is a full-screen desktop with three zones. On the left is the **conversation** with the agent. In the middle is the **presentation** zone, where the agent's output appears as tabs: Markdown, diagrams, PDF pages, images, and whole GUI applications, Xenith among them. On the right is the **context** zone, which shows what the agent can reach: its tools, the paths bound into its namespace, and a catalog of resources that are available but not mounted.

The context zone is the part we care most about. In most agent interfaces, what the agent can touch is configuration hidden somewhere. Here it is on screen, and it changes as you click. Toggle a tool off and the model stops seeing its schema on the next turn. Bind a directory from the file browser and the agent finds it under `/n/local` on the next turn, with the path named in its system prompt.

## The UI is a file server

This is Inferno, so the interface is a file server before it is anything else. The [first commit](https://github.com/infernode-os/infernode/commit/1b5a5d5f971c1b4276492571131195f3717a2fde), on 23 February, was `luciuisrv`, a Styx server that holds all UI state as a 9P tree. The renderer is only a view of it:

```
/n/ui/
    ctl  event
    activity/{id}/
        conversation/   ctl  input  0 1 2 ...
        presentation/   ctl  current  {artifact}/type label data
        context/        ctl  resources/  gaps/  background/
```

A message is posted by writing to `conversation/ctl`. A reader blocks on `conversation/input` until the user types something. An artifact is a directory with a type, a label and its data. Because there is no drawing code in the server, it can be tested headless, and it is: 20 regression tests [cover](https://github.com/infernode-os/infernode/commit/69571d663daac12c0ab4d77dbfcb64637ee4a6c7) every ctl command, event delivery to each zone, and artifact updates. It also means anything that can write a file can drive the UI: a shell script, a test, or the agent's own `present` tool.

The renderer was later [split](https://github.com/infernode-os/infernode/commit/5d58fceb4cc2f2a4430f158ecf199cb26b3dcb52) into a tiling window manager (`lucifer`) and one module per zone: `luciconv`, `lucipres` and `lucictx`. The presentation zone is an ordinary window-manager client, which is how other Inferno GUI programs [can run as tabs](https://github.com/infernode-os/infernode/commit/172b7ac8d16810f3df0471cb8a0bbf0c76b3b28d) inside it.

## The bridge to the model

The same day came [`lucibridge`](https://github.com/infernode-os/infernode/commit/b42759b0f7a377a1674e09c8011632daa6556cc4). The model is a file server too: `llm9p` presents the model API at `/n/llm`, where a session is cloned from `/n/llm/new`, a prompt is written to `/n/llm/{id}/ask`, and the reply is read back from the same file. `lucibridge` sits between the two trees. It blocks reading the conversation's `input`, and it writes the answer back as a message from Veltro.

Twenty minutes later the bridge [ran the full Veltro agent loop](https://github.com/infernode-os/infernode/commit/1908643735aef930bd4984a8bcc9193c638b743e) instead of plain chat. It uses the same `agentlib` that the command-line agent uses: discovering the namespace, building the system prompt, and running query, tool call, result and repeat. It falls back to chat-only relay when no `/tool` is mounted. Tools are served by `tools9p` at `/tool`, which turns out to be the piece that holds everything together. The GUI and the bridge run as separate processes with separate namespaces, so a `bind` in one does not affect the other. Both inherit `/tool` from the shell that started them, so `/tool/ctl` serves as the configuration bus: the context zone writes `add`, `remove` or `bindpath`, and the bridge rereads `/tool/tools` and `/tool/paths` at the start of each turn. The reasoning is written up in [PATH-MANAGEMENT.md](https://github.com/infernode-os/infernode/blob/master/docs/PATH-MANAGEMENT.md).

## The namespace rules

Several design decisions in Lucia follow directly from the namespace model:

- **The agent cannot grow its own namespace.** When the user clicks [+] on a catalog entry, Lucia itself dials and mounts it. [The agent's namespace hides `/n/ui/ctl`](https://github.com/infernode-os/infernode/commit/8a6e46706703c3719b2c84fe4674ddf5b0860251), and the agent's `mount` tool only returns an error saying this is a user-only operation.
- **No wholesale grants.** The UI is served at `/n/ui`, not `/mnt/ui`. `/mnt` is user-controlled and arbitrary services can be mounted there, so granting it to the agent's tools would be an escape hatch. [`/n/ui` follows](https://github.com/infernode-os/infernode/commit/08f9fe20056fea6967197fbf69fc3a6fa5675f7f) the same pattern as `/n/llm` and `/n/speech`, and the namespace constructor grants it as it grants them.
- **Restriction at the moment of use.** [Each tool invocation gets a namespace built fresh](https://github.com/infernode-os/infernode/commit/278661b7ed39afa7d9eaaeaa0a6679e359fdc608) from the paths granted at that moment, so a grant made mid-session or a binding removed mid-session takes effect on the next call.
- **Writes that can be undone.** [`cowfs`](https://github.com/infernode-os/infernode/commit/ca620630701751d0c8d869be60a76ddc22c0b222) is a copy-on-write Styx overlay. Reads fall through to the base, writes go to an overlay, and deletes leave whiteouts.
- **Safe defaults.** The app starts the agent with tools that read, search, write and present. `exec`, `launch`, `spawn`, `git` and `mail` can run commands, push to repositories or send mail, so they are off until the user turns them on in the context zone.

## What shipped in the merge

By the time #41 merged, Lucia had streaming replies, Markdown and Mermaid rendering, PDF and image tabs with zoom and pan, and [voice](https://github.com/infernode-os/infernode/commit/225abe6c6335c761c753e36a17a1753fcad9c790) through `speech9p` (a mic button, Ctrl+Space, and spoken replies). It also had a small editor, `luciedit`, that the agent can drive through files. There are [two themes](https://github.com/infernode-os/infernode/commit/2c2dcbf85f8855f164ed57a4a1e0c8697ea38a1b), Brimstone (dark) and Halo (light, in Acme's pale yellow), stored as flat files in `/lib/lucifer/theme/`, so a new theme is a new file. The whole stack is four programs started from a shell: `luciuisrv`, `tools9p`, `lucibridge` and `lucifer`. The data flows are documented in [ARCHITECTURE.md](https://github.com/infernode-os/infernode/blob/master/docs/ARCHITECTURE.md).

Xenith is not going anywhere. It is still where we write code, and it now runs as a tab inside Lucia. The difference is that a person who has never seen Acme can sit down, type a sentence, and watch an agent work inside a namespace they can see and change. That is the audience the next stage of the project depends on. It also raises the stakes on the claim underneath it all: a desktop that invites people to hand an agent their files has to be right about what the agent cannot reach.
