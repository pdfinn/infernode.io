Every time we explain InferNode, the same question comes back: who writes Limbo? It is a fair question. Limbo is the right language for Inferno®: it was designed with the Dis virtual machine, and its channels, modules and type-safe loading are what make per-process namespaces practical to program against. But the people who know it would fit in a small room. Inferno's security model is the reason we are here, and if only that room can build on it, the model will not get far.

Go is Limbo's close relative. It comes out of the same Bell Labs lineage, with channels, lightweight processes, garbage collection, and a taste for small interfaces and plain types. On 21 February we set out to see how much of the language gap a compiler could close. Two days later [`tools/godis` merged](https://github.com/infernode-os/infernode/pull/16): a compiler written in Go that turns Go source into ordinary `.dis` modules the emulator loads like any Limbo program.

## Don't bring a runtime

The usual way to run Go somewhere new is to port its runtime: scheduler, allocator, growable stacks. We did not, because a ported runtime would sit inside Dis as a guest, opaque to the namespace and to the VM. Instead `godis` maps Go onto what Dis already has:

| Go | Dis |
|---|---|
| `go f()` | `SPAWN` |
| `chan T`, send, receive | `NEWC`, `SEND`, `RECV` |
| `select` | `ALT`, `NBALT` |
| `string` | Dis strings |
| `[]T` | Dis arrays |
| `panic`/`recover` | exception handler tables, `RAISE` |

A compiled Go program is therefore a Dis module like any other. The same VM schedules and collects it, it is bound by the same namespace, and it can share channels with Limbo because they are the same channels. For our purposes that is the point. A Go program under InferNode can reach exactly what its namespace holds, the same as anything else.

The pipeline adds no IR of its own. `go/parser` and `go/types` front-end into `golang.org/x/tools/go/ssa`, the compiler's only external dependency. A pre-pass collects closures, bound-method wrappers, `init` functions and the concrete types behind each interface. Then each SSA function is lowered block by block into Dis instructions and assembled into a module with type descriptors and pointer maps. Several features came free because SSA had already desugared them: `goto`, labelled `break`, `fallthrough`, three-index slices. [Generics](https://github.com/infernode-os/infernode/commit/7c6c0fc6aa982b5e5381b459004f04b0ddc07b1a) were a builder flag: `ssa.InstantiateGenerics` monomorphizes each instantiation, and the compiler compiles the copies. [`recover`](https://github.com/infernode-os/infernode/commit/6658db6550191dd7094fabcf34cecae4c6fc5af6) maps onto Dis handler tables. That work also turned up an ARM64 detail: `sdiv` returns 0 on division by zero instead of trapping, so integer division now gets an explicit check that raises.

## Writing down every bug

Two days from nothing to generics and `recover` is a pace we could not have reached without AI assistance. It brings a risk we have learned to take seriously. Whoever picks the work up next, a person or a fresh assistant session, has none of the context in which the last bug was understood, and can bring it straight back. So the [compiler's README](https://github.com/infernode-os/infernode/blob/932f5bb4f5eca6c98ca6b953409a20de830f9918/tools/godis/README.md) includes a bug log: 28 entries at merge time, each with symptom, cause and fix. Next to it is a list of "critical patterns", each one, in the README's words, "a class of bug that is easy to reintroduce". Most of them are about Dis, not Go:

- **A zero-valued operand is not "no operand".** Addressing mode 0 means absolute module-data addressing, so a forgotten operand reads from an arbitrary module-data address.
- **Operand order is `OP src, mid, dst` with `dst = mid OP src`.** Subtraction, division, modulus and some loop-exit branches all came out reversed at first.
- **Nil is H, all ones, not 0,** for slices, maps, channels and function values. Interfaces are the exception: they are two words we lay out ourselves, and both must be zeroed explicitly.
- **Only pointer slots in a frame are initialized.** Scalars can hold whatever the previous call left there.
- **An address from LEA is not a heap pointer.** If it is stored in a pointer slot, the collector will try to reference-count it.

This is documentation as a defence. A fast team that cannot remember the last bug will just keep fixing it.

## What it costs

A [16-benchmark suite](https://github.com/infernode-os/infernode/commit/17576bc7d6225b87d52ebe5dba72a70e4ff7587e), recorded in [BENCHMARKS.md](https://github.com/infernode-os/infernode/blob/master/docs/BENCHMARKS.md), runs each program as native Go, as `godis` output and as hand-written Limbo, under the JIT and the interpreter, with one warm-up and five timed runs. Some rows from a Jetson AGX Orin (Cortex-A78AE, Go 1.23.4, 512 MB Dis arena), mean times in milliseconds:

| Benchmark | Native Go | GoDis JIT | GoDis interp | Limbo JIT |
|---|---|---|---|---|
| fib | 50 | 547 | 2666 | 676 |
| sieve | 19 | 85 | 863 | 55 |
| channel | 11 | 6 | 32 | 4 |
| closure | 34 | 332 | 1697 | 40 |
| interface | 91 | 152 | 741 | 344 |
| spectral_norm | 48 | 720 | 3894 | 295 |

- On compiled Go, the median JIT-to-interpreter ratio is 0.17, roughly 6x, and tight loops reach about 10x. The JIT ports we finished earlier this month carry their weight here too.
- Native Go is 3x to 82x faster than the `godis` JIT, with a median around 10x, and the gap is widest on floating point and deep call chains.
- Hand-written Limbo usually beats compiled Go on the same VM. Our generated code has more temporaries and no peephole pass. Closures are the worst case: `godis` dispatches dynamic closures through a chain, where Limbo has native function references. Interface dispatch is the exception, and there `godis` is faster than the Limbo version.
- Both Dis versions beat native Go on the simple channel send/receive benchmark. We would not read more into that one result than it says.
- `strcat` under the JIT ran out of the 512 MB arena, because the generated code allocates intermediate strings faster than they are reclaimed.

## Where it stands

There is no reflection and no cgo. Maps are sorted arrays. Everything compiles into a single `.dis`. Standard-library coverage is growing quickly on a working branch, which now has stubs for more than 115 import paths. Most of those stubs give types and signatures so programs type-check. They are not reimplementations, and a program that leans on a stubbed function will compile and then not behave like Go.

So this chapter ends with a working answer rather than a final one. Go programs with goroutines, channels, generics, closures, interfaces and `recover` run on Dis, inside the namespace model, within an order of magnitude of native Go on most of the suite. Whether that brings Go programmers to Inferno depends on what they try to build. Either way, it has already shown us how to keep moving this fast without forgetting what we learned along the way.
