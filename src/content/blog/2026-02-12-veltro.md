Today Veltro, the agent we have been building inside InferNode, works the way we set out for it to work. You open a Veltro window in Xenith, our fork of Acme, type a request or press `Voice` and say it, and the agent reads files, opens windows, writes into them and answers you aloud. Nothing in that loop is an SDK or a plugin interface. The model, the tools, the editor's windows and the speech engine are all files in a namespace, and the agent can use exactly what that namespace contains. We are calling 12 February Veltro's birthday.

## The editor was the starting point

InferNode began as an attempt to make Acme an AI text editor. Acme's windows are files, so anything that can read and write files can drive it, and a language model can do both. Xenith keeps that: every window is a directory with `body`, `tag`, `ctl` and `event` files. Over the past fortnight it has also learned to render Markdown, HTML and PDF content in place ([#7](https://github.com/infernode-os/infernode/pull/7), [#8](https://github.com/infernode-os/infernode/pull/8), [#10](https://github.com/infernode-os/infernode/pull/10), [4d10ec4d](https://github.com/infernode-os/infernode/commit/4d10ec4d)), so the documents an agent works on can be read by a person in the same window system.

Veltro is the agent that lives there. `repl` ([a1426b20](https://github.com/infernode-os/infernode/commit/a1426b20)) opens a Xenith window with `Send Voice Clear Reset Delete` in its tag and keeps a conversation going with the model. Without Xenith it falls back to a line-oriented terminal. The agent's `xenith` tool ([59ce7a0e](https://github.com/infernode-os/infernode/commit/59ce7a0e)) lets it create windows, write to their bodies and tags, read them, and set a coloured status so the person can see at a glance which window holds results and which an error. We deliberately do not paste the user's windows into the prompt. The system prompt tells the agent that open windows are a shared workspace and that it should look at what the user has open before acting ([b2b373de](https://github.com/infernode-os/infernode/commit/b2b373de)).

## Voice, as a file server

[PR #11](https://github.com/infernode-os/infernode/pull/11), merged on 11 February, added `speech9p`, a 9P server that mounts at `/n/speech` and serves four files:

```text
/n/speech/ctl      read the configuration; write "engine api", "voice nova", ...
/n/speech/say      write UTF-8 text to speak it; read the status of the last one
/n/speech/hear     write "start" to record; read the transcription
/n/speech/voices   the voices the current engine offers
```

Engines are pluggable behind `module/speech.m`. The `cmd` engine runs host programs through the `cmd(3)` device: `say` on macOS, `espeak-ng` on Linux, PowerShell's `System.Speech` on Windows. The `api` engine speaks to an OpenAI-compatible HTTP endpoint. The interface is documented the usual way, in [`speech(4)`](https://github.com/infernode-os/infernode/blob/7ce9032286bfc6e300fadada5dc80a5497a35482/man/4/speech).

The following night made it work end to end on the Mac. [549c9132](https://github.com/infernode-os/infernode/commit/549c91321410286fb2378af05e3554d3a4a4b4d8) corrected how `speech9p` drives the `cmd` device (write `exec` to the clone file, read the output from the data file) and made the profile start both services at boot: `llm9p`, which serves the model at `/n/llm`, and `speech9p`. [d03e6427](https://github.com/infernode-os/infernode/commit/d03e6427) added the other direction: on macOS, `ffmpeg` records from the microphone and `whisper-cli` transcribes it, and the `Voice` tag button (or `/voice` in the terminal) records a request and sends the text to the agent. [7056d6b7](https://github.com/infernode-os/infernode/commit/7056d6b7) made spoken replies carry the whole answer rather than stopping at the first blank line, with Markdown stripped so the voice does not read out asterisks.

The agent never sees `/n/speech`. It sees two tools, `say` and `hear`, and only if they are granted. Speaking is a capability like any other.

## Tools are files, and only the granted ones exist

Veltro's tools are served by `tools9p` ([1e89070b](https://github.com/infernode-os/infernode/commit/1e89070b27f06412d056c8b971c43573590a314a)). The caller starts it with an explicit list, and it serves those tools and nothing else:

```sh
tools9p read list find search xenith say hear &
veltro 'list the files in /appl/cmd'
```

The agent writes arguments to `/tool/<name>` and reads back the result. A tool that is not on the list is not refused; it is absent. The system prompt states the rule plainly to the model: "Your namespace IS your capability set. Everything you can see exists. Everything you can use is available. If something isn't in your namespace, it simply doesn't exist."

That is the design principle, and it applies below the tools as well. The agent's whole namespace is constructed, not filtered.

## Constructing the namespace

The namespace construction going in with Veltro this week ([07bd9403](https://github.com/infernode-os/infernode/commit/07bd9403c45fd189853652eedb6c98b9b745ad96)) rests on one primitive, `restrictdir(target, allowed)`:

```text
1. make an empty shadow directory under /tmp/veltro/.ns/shadow/
2. for each allowed item:   bind target/item -> shadow/item   (MREPL)
3. bind shadow -> target                                        (MREPL)
```

After step 3, `target` contains exactly the allowed items. Everything else is not hidden behind a check; it is gone from that process's view of the tree. Veltro begins with `pctl(FORKNS)`, so the caller's namespace is unaffected, and then `restrictns()` applies the primitive in turn: `/dis` keeps only the runtime libraries and Veltro's own modules, `/dis/veltro/tools` only the granted tools, `/dev` only `cons` and `null`, `/n` only `llm` (and `mcp` when MCP providers are granted), `/lib` only `veltro`, and `/tmp` only `veltro`, last, because the shadow directories live there. The host filesystem at `/n/local` is unmounted first. Shell access is a capability too: if no shell commands are granted, there is no `sh.dis` to run, and if `cat` and `ls` are granted, those are the only commands that exist.

Why bind-replace over the other ways of building a small namespace? It copies nothing, it leaves nothing on disk to clean up, and it starts from a namespace that already works, so there is no bootstrap problem of how a process reaches the modules it needs after its namespace is emptied. It is also short enough to read in one sitting.

Sub-agents follow from it directly. The `spawn` tool forks the already-restricted namespace and restricts it further, so a child can only ever have less than its parent. Before the child runs, `spawn` also gives it a fresh process group with an empty service registry (`NEWPGRP`), an empty environment so no inherited secrets survive (`NEWENV`), only the file descriptors it should keep (`NEWFD`), and `NODEVS`, so it cannot name `#U`, `#p` or `#c` to reach the host disk, other processes or the console device behind the namespace's back. The security suite checks these properties: nine security tests and three concurrency tests.

## What it is like to use

The first thing a new user can do is run the tour ([3fa42852](https://github.com/infernode-os/infernode/commit/3fa42852)). Veltro conducts it itself: it speaks a welcome, opens a `Tour` window, explains Xenith's three mouse buttons, creates a `Scratch` window with text to try them on, and checks with the user before moving on. The same commit added `/lib/guide`, an Acme-style page of commands to middle-click and paths to right-click, and made the `search` and `find` tools give up on directories macOS will not let them read instead of hanging.

## Next

Veltro now has a voice, an editor and a namespace that defines it. The work ahead is to make the agent loop more robust against models that answer in prose when a tool call is expected, to keep the allowlists as short as the tasks allow, and then to attack the construction directly: a restricted agent should not be able to name anything outside its tree, by any route.
