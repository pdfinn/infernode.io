For eleven weeks InferNode has been something we built from source and ran ourselves. On 9 April we tagged [v0.1](https://github.com/infernode-os/infernode/releases/tag/v0.1), our first public release: something a stranger can download and run.

The bet has not changed since January. Agents will be handed tools, and sooner or later one will reach for something it should not, so what an agent can reach should be decided by something underneath it: a per-process namespace where anything not bound in does not exist. Inferno® had that model, but its last upstream release was around 2015, with a 32-bit hosted emulator and JITs built for the hardware of their time. Bringing it forward has also been an experiment in AI-assisted development, and most commits in this tree carry a `Co-Authored-By` trailer naming the assistant they were written with. v0.1 is the first point at which anyone outside can judge the result.

It is two downloads: a signed and notarized `.dmg` for Apple Silicon with the SDL3 GUI, and a headless Linux AMD64 tarball. Windows, the release notes say, will ship in a future release. The [CHANGELOG](https://github.com/infernode-os/infernode/blob/master/CHANGELOG.md) lists what is inside:

- **Veltro**, the agent, with tool use, delegation and sub-agents that each run in their own namespace.
- **Namespace isolation** as the security model: each agent sees only the resources it was explicitly granted. The isolation properties are modelled in TLA+ and SPIN and checked with CBMC under `formal-verification/`.
- An **ARM64 JIT** for Apple Silicon and Linux ARM64 boards such as the NVIDIA Jetson.
- **Xenith**, our Acme fork, and **Lucia**, a three-zone GUI (conversation, presentation, context).
- **Secstore** for encrypted key storage, with PAK authentication.
- LLMs, speech, tools, the wallet and the UI all served as **9P file systems**.
- Preliminary **ML-KEM (FIPS 203) and ML-DSA (FIPS 204)** implementations.

Most of the last week, though, went into one problem: turning a source tree that runs as `emu -r.` into something a stranger can double-click.

## Signing and the JIT

The release workflow now signs `o.emu`, `limbo`, `mk` and `llm9p` with a Developer ID certificate and submits the result to `notarytool`, so Gatekeeper opens it without a warning ([e36c830](https://github.com/infernode-os/infernode/commit/e36c830d81bf096081126ef9e29d95c0f653c836)).

The first signed build broke the JIT. Notarization requires the hardened runtime, and the hardened runtime refuses `MAP_JIT` by default, so `emu -c1` failed at startup with `disinit error: Invalid argument`. The fix was two entitlements on the emulator: `allow-jit` and `allow-unsigned-executable-memory` ([9353077](https://github.com/infernode-os/infernode/commit/93530775218b5c33724a7eb7f133f97cdde1dae8)). We considered shipping the interpreter only on macOS. We didn't, because the JIT is a large part of why a Dis VM is a reasonable way to run agents on small machines.

## The DMG is read-only, and so is the bundle

Our first layout was a conventional self-contained `.app` ([d86d434](https://github.com/infernode-os/infernode/commit/d86d434272a08dd682e33c1cb08d109cb21b7767)). The emulator and the SDL3 dylib live in `Contents/MacOS/`, the Inferno tree (`dis/`, `lib/`, `fonts/` and the rest) lives in `Contents/Resources/`, and on first launch the launcher copied the whole runtime to `~/.infernode` so it had somewhere to write.

That works, but it ran into macOS in several ways. A DMG is mounted read-only. An app launched from a mounted DMG gets *translocated* to a temporary path before it runs, so a check for `/Volumes/` alone misses it ([60bbafb](https://github.com/infernode-os/infernode/commit/60bbafbbe142674d924ed57a6058497f05c3b921)). We now show a native dialog asking the user to drag the app somewhere writable first ([dd65b0e](https://github.com/infernode-os/infernode/commit/dd65b0ef2c02a91f3140e2e0e14cb70253160be1)). The copy itself was the bigger problem: two copies of `dis/`, and a sync step on every upgrade to keep them consistent.

What we shipped instead ([3879eba](https://github.com/infernode-os/infernode/commit/3879eba3249db6c5faa7085e0dcd5bb186b72ac5)) is the Plan 9 answer. `Contents/Resources/` is the emulator's root, and it is never written. The shell profile builds a sparse writable directory and union-mounts it over the few paths that hold user state:

```sh
infhome=$ghome^/.infernode
bind -bc $infhome/usr/inferno/secstore /usr/inferno/secstore
bind -bc $infhome/lib/ndb              /lib/ndb
bind -bc $infhome/lib/lucifer/theme    /lib/lucifer/theme
bind -bc $infhome/lib/veltro           /lib/veltro
bind -bc $infhome/tmp                  /tmp
```

`bind -bc` puts the writable directory in front and makes it the place where files are created. Reads fall through to the bundle, and writes land in the overlay. An upgrade replaces the bundle and leaves user state alone. The macOS launcher went from 109 lines to 21, and the dynamically generated boot script was replaced by a static `lib/lucifer/boot.sh`.

One bug here is worth recording. The first version created the overlay directories with the host shell (`os sh`), outside Inferno. The binds then failed silently, and writes went into the bundle. The host tree is reached through `trfs`, which had already cached negative lookups for those paths, so when the directories appeared behind its back the binds walked into stale entries. Creating and seeding the overlay through Inferno's own `mkdir` and `cp` keeps the cache coherent ([960c67a](https://github.com/infernode-os/infernode/commit/960c67af2724e846291df1c52f5fab580654cf34)). The same commit renamed the overlay from `~/.inferno` to `~/.infernode` so that it can't collide with an upstream Inferno install.

## First run without an LLM

A fresh install has no API key and no local model, so the agent has nothing to talk to. Early builds treated a missing `/n/llm` as fatal. Now the boot polls for it, and the conversation zone shows a dialogue tile with two buttons: *Set up API Key*, which opens Keyring in the presentation zone, and *Use Local LLM (Ollama)*, which opens Settings ([3912139](https://github.com/infernode-os/infernode/commit/39121397623b3d9ea3f722768198b118a8fee906)). The commit message states the rule we followed: the user starts the action, not the AI.

Checking whether the LLM is configured was harder than it sounds. `mntgen` creates mount-point stubs on demand, so `ftest -d /n/llm` is always true. The boot script now checks for `/n/llm/new`, a file only a running `llmsrv` serves. The setup dialogue checks factotum for the key itself, which separates "not configured" from "configured but unreachable".

## Known issues

These are copied from the CHANGELOG:

- Secstore key loading can fail intermittently on a cold boot because of `trfs` cache timing. `boot.sh` warms the cache with an `ls` of the secstore directory before logon as a workaround.
- Models without tool use (llama2, for example) return empty responses. Use a model that supports tools, such as llama3.2, qwen2.5 or mistral.
- Presentation rendering is tightly coupled to the `lucipres` window. We plan to split it out into a separate app.

## What landed right after the tag

Some work was merged to master on the same day, after the tag, and will ship in the next point release:

- Release artifacts signed with Sigstore cosign (keyless OIDC), with verification instructions in the release notes ([c945f32](https://github.com/infernode-os/infernode/commit/c945f32f9fe9baf2de0bedc614e0c46dc307a0c1)).
- In the same change, two loader fixes. An `acheck()` guard before array allocation in the Dis module loader stops a crafted `.dis` with a huge array size from overflowing an integer. And the bounds check in `so_gethostbyname()` now runs before the array access instead of after it.

## What this week taught us

Two lessons from the run-up to the tag go beyond packaging.

The first is that the old model keeps winning when we let it. The installer problem looked like it needed an installer. In the end it needed a union mount and a few `bind -bc` lines, the same mechanism the agents' sandboxes are built from. When we reach for something outside the system, it is usually a sign we have not yet looked hard enough inside it.

The second is about working with an AI assistant at this pace. It is fast, and it is not infallible in the ways that matter here. On 5 April a set of changes to the dialogue tiles silently reverted partway through a long working session: the assistant's context was compacted, the earlier edits fell out of its working memory, and later recompiles rebuilt from stale source. The fix commit says exactly that ([41f65bb](https://github.com/infernode-os/infernode/commit/41f65bb26c10f722443a6e7a5975f8c7cc994fcc)). We keep finding that the defence is the same as for any fast collaborator: small commits, tests that exercise what users actually do, and a human reading the diff.

## Where this goes next

v0.1 is a beginning, not a claim of completeness. The Linux build is headless (`./build-linux-amd64.sh` gives you the SDL3 GUI) and Windows is not here yet. The namespace model is in place and modelled; what it needs now is people trying to break it. If something breaks, please [open an issue](https://github.com/infernode-os/infernode/issues).
