The Plan 9 world has never had a real, modern, standards-compliant web browser. Inferno® had Charon, a browser written in Limbo in the 1990s, and it renders the web of the 1990s. To read the web as it is written now, Plan 9 and Inferno® users have had to leave the system for a host browser.

That was the last big gap we set out to close this year, and in some ways it was the hardest test of the bet behind the project. A browser engine is a different kind of problem from a JIT or a kernel port. The specifications run to thousands of pages, the tests number in the tens of thousands, and the large browsers are kept up by very big teams. The question was whether a small team working with AI coding assistants could bring Charon back from the dead and make it modern, standards-compliant, fast enough and usable. As of this week, we think the answer is yes, with a list of gaps we can name.

## Where Charon started

In March we brought Charon back into daily use. [48e24451](https://github.com/infernode-os/infernode/commit/48e24451) made it something an agent could drive: control files under `/tmp/veltro/browser/`, a Veltro `charon` tool, and HTTPS over our TLS 1.3 client. Over the following weeks we added CSS to the old renderer, aimed at rendering Wikipedia properly, and made Charon the HTML renderer behind Xenith.

That work also showed where the old design stops. Charon's renderer is an "item list": the HTML lexer feeds a builder that emits a flat stream of text, image, rule and table items, and layout breaks the stream into lines. It has no document tree and no box tree. CSS had been bolted onto the stream, but the model cannot express what CSS means. An empty `<div>` with a width, height and background has no items, so it does not exist. Flex items stack instead of forming a row. There is no tree to match `:has()` or sibling selectors against. On 30 September we wrote 32 small conformance fixtures, in the "green means pass, red shows through on failure" style, and the old engine passed 6 of them ([0e6d6f15](https://github.com/infernode-os/infernode/commit/0e6d6f15)). Its ~16,000 lines could not be patched into a CSS engine.

## What would Bell Labs build?

That is the question at the top of the design document, [CHARON-ENGINE.md](https://github.com/infernode-os/infernode/blob/master/docs/CHARON-ENGINE.md). The answer is not a smaller Chrome. It is what Plan 9 does with any large program: find the data structures, make each stage a small piece with a plain interface, and let the namespace do the integration.

```
bytes ─ html ─▶ Doc ─┐
                     ├─ style ─▶ styled Doc ─ layout ─▶ Box tree ─ paint ─▶ display list ─▶ draw(3)
css text ─ css ─▶ Sheet ┘
```

The engine is four data structures: a document tree, a style sheet, a box tree and a display list. A document is an array of nodes linked by integer indices, with element names interned to small integers at parse time. That leaves no cycles for the garbage collector to chase, and the JIT compiles index arithmetic well. Each stage is one module with one entry point, and where a standard defines an algorithm, the module follows its steps and cites the section. Chrome and form controls are Tk widgets, themed like everything else, and page content is painted through the draw device's anti-aliased paths, so rounded borders, SVG and outline text all come from one rasteriser.

## Milestone by milestone

The engine landed on 1 October, one stage per commit, and was merged on 2 October as [#754](https://github.com/infernode-os/infernode/pull/754).

- **HTML** ([b36fe194](https://github.com/infernode-os/infernode/commit/b36fe194)): the WHATWG tokenizer and tree construction, section by section, with SVG and MathML foreign content and all 2,231 named character references. Tree-construction cases in html5lib format all pass. A 766 KB page parses in 460 ms under the JIT, into 84,000 nodes.
- **CSS and the cascade** ([a25e7d18](https://github.com/infernode-os/infernode/commit/a25e7d18), [1ff42681](https://github.com/infernode-os/infernode/commit/1ff42681)): Syntax 3, Selectors 4 including `:has()` and `:nth-child(An+B of S)`, nesting, `@layer`, `@media` and `@supports`, custom properties with cycle detection, `calc()`, and every colour syntax in CSS Color 4.
- **Layout and paint** ([f73f2de1](https://github.com/infernode-os/infernode/commit/f73f2de1), [b6801e20](https://github.com/infernode-os/infernode/commit/b6801e20), [1d2d54a6](https://github.com/infernode-os/infernode/commit/1d2d54a6), [ea912004](https://github.com/infernode-os/infernode/commit/ea912004)): block and inline formatting with margin collapsing, floats, positioning and stacking contexts, flexbox, grid, and CSS 2.2 tables. Text is drawn from TrueType outlines (DejaVu now ships in the tree) at any size, weight or slant. Inline `<svg>` followed ([0aab735e](https://github.com/infernode-os/infernode/commit/0aab735e)), and all 46 render fixtures passed.

## The browser is a file server

The network is a grant. The engine never dials anything itself. It fetches through `webfs` at `/mnt/web`, so what a browser can reach is literally a mount. [185deddb](https://github.com/infernode-os/infernode/commit/185deddb) gave `webfs` what a browser needs: concurrent fetches, an RFC 6265 cookie jar readable and writable as `/mnt/web/cookies` (so a browsing session is a mount), and gzip and deflate decoding.

What the browser shows can be read, and what it does can be driven, through `/mnt/charon` ([580609bc](https://github.com/infernode-os/infernode/commit/580609bc), [8bbae482](https://github.com/infernode-os/infernode/commit/8bbae482)):

```sh
; echo open file:///tests/charon/wpt/flex-row.html > /mnt/charon/ctl
; cat /mnt/charon/status
done
; cat /mnt/charon/dom/5/style | grep display
display flex
```

An agent browses with `cat` and `echo`, and a test asserts layout with `grep`. The capability split follows from the files. `text`, `links`, `forms` and `dom/` are reads of what was already fetched. `ctl` makes the browser fetch, so granting it grants network reach. Agents run without access to `#s`, so they cannot attach the posted session themselves. `tools9p` mounts it for the `charon` tool only, and `nsconstruct` refuses `/mnt/charon` as a general path grant. `wm/charon` is now the new engine, with a Tk location bar and form controls as real Tk widgets placed over their boxes.

## Measured, not eyeballed

A browser that "looks right" to its authors tells you little, so Charon is judged against references with the tools in [`tools/ref`](https://github.com/infernode-os/infernode/blob/master/tools/ref/README.md) ([1d9620f8](https://github.com/infernode-os/infernode/commit/1d9620f8)). Over 18 CSS directories of web-platform-tests, test and reference are both rendered by Charon and compared pixel for pixel. The first run passed 37.8%. Fixing what the references found took it to 46.4% ([3eaa1c5d](https://github.com/infernode-os/infernode/commit/3eaa1c5d)). Under a stricter count it stands at 46.7% of 12,626 ([4ad5fcb9](https://github.com/infernode-os/infernode/commit/4ad5fcb9)). That count excludes the 1,267 tests that contain script even when their pixels match, flags passes where nothing rendered, and retries a failing page once. Against headless Chromium with scripts off, pypi.org's home page went from 47.8% of pixels differing to about 7%, mostly anti-aliasing.

Acid2 now renders correctly. Its only differences from Chromium are anti-aliasing. Along the way the engine gained `@font-face` with TrueType, WOFF and WOFF2, OpenType CFF outlines, and Brotli (RFC 7932) in Limbo, tested against the reference encoder at every quality level.

A browser also turned out to be a good test of everything underneath it. A GSUB parser passing a bad offset showed that the amd64 and arm64 JITs had been compiling array indexes with no bounds checks at all. [27d0027c](https://github.com/infernode-os/infernode/commit/27d0027c) turns them on. A grid column that collapsed only under the JIT led to [9f096691](https://github.com/infernode-os/infernode/commit/9f096691): `ref T` with no initializer had never zero-filled its scalar members. Both fixes landed on 2 October, with tests.

## What is not done

JavaScript is the largest gap, and it is deliberate. There is no script engine yet. The design leaves exactly one seam for one: the document's mutation interface is the only way to change the tree, and the HTML parser itself uses nothing else, so a script host would be just another caller, running in its own process. Until then, `<script>` elements are kept in the tree but not executed.

The failures also name other gaps: bidi reordering, vertical writing modes, complex-script shaping, GPOS kerning, sub-pixel layout, iframes and an HTTP cache. The [hand-off notes](https://github.com/infernode-os/infernode/blob/dd5fb283/docs/CHARON-HANDOFF.md) list 36 tests that passed before and now fail, along with what is known about each. The old engine still backs Xenith's render mode until the final milestone removes it. The engine is also already larger than the 12,000-line budget the design set for it.

None of that changes the result. Inferno® now has a browser engine that follows the standards section by section, can be checked against the same tests the major engines use, and exposes the page as files that people, scripts and contained agents can all use. The rest is a list of things to finish.
