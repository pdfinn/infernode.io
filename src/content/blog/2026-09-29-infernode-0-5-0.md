At the start of September, InferNode ran on a bare Raspberry Pi 3B+, [nine days into a native port](/blog/infernode-on-bare-metal/), and the network was slow. A kernel that has drawn a window manager once is not one we can ship. So for most of September the question was simpler and harder: would it keep running?

[InferNode 0.5.0](https://github.com/infernode-os/infernode/releases/tag/v0.5.0), tagged on 28 September, says yes, within limits it states. The native kernel in `os/` boots the 3B+ from its SD card to the Lucifer desktop, with USB input, HDMI, Wi-Fi, Bluetooth and Ethernet. The arm64 `virt` machine and the Raspberry Pi 4 build and boot under QEMU in CI. RISC-V, [covered separately](/blog/risc-v/), is in this release too.

We set one condition before the tag: the kernel had to run for 48 hours on the board. This chapter is about what meeting that condition turned up. None of it would have shown in a unit test, and some of it was not visible from inside the system at all. It is also about a security fix that has nothing to do with bare metal, and that we are not proud to have needed.

## A lock loop, five hours in

Five hours into the pre-release soak, the Pi panicked:

```
lock loop 0x23fd98 key 0x1 pc 0xcba80 held by pc 0x0   (two cores)
panic: lockloop        ether0tx, ether0rx: lock <- tsleep <- chanwait
```

The address `0x23fd98` is `talarm`, the timer-sleep lock. "Held by pc 0" meant the lock was held by a process that was not running. The USB host driver's `chanwait()` calls `tsleep()` at `splhi`, so it spins for `talarm` with interrupts off. Every ordinary `tsleep()` takes `talarm` with interrupts on, so the clock interrupt can preempt the process holding it. An earlier fix guarantees that a process preempted while running resumes on the core it left. If that core then runs the Ethernet receive process, and that process spins with interrupts off, the holder can never get back.

We reproduced the panic on the board before fixing it. A stress program ran 32 Dis threads in `sys->sleep(1)`, about 30,000 `tsleep()` calls a second. The lock loop came at 40, 65, 90, 115 and 125 seconds, in five runs out of five.

The first fix was Plan 9's rule: don't preempt a process that holds a spin lock ([#682](https://github.com/infernode-os/infernode/pull/682)). It stopped the panic, but inbound TCP fell from 147-154 Mbit/s to 16-28. We bisected on the board and found that the throughput collapsed with only about ten deferred preemptions a second. We could not explain why so few cost so much, and we decided a scheduler change we did not understand would not go into a kernel about to be released. We reverted it whole.

The evidence supported a narrower fix. Every lock loop, the soak's and six out of six under the stress test, was on `talarm`. It is the one lock that is spun for with interrupts off but taken with them on. `tsleep()` now takes it with `ilock()`. Inbound TCP measured 159-161 Mbit/s on the board afterwards. The soak was restarted and ran from 21 September 13:13 to 23 September 13:59 with no panics and no reboots. It pushed 290 of 290 inbound transfers at a mean of 144.7 Mbit/s, the acceptance batteries passed twice, and memory showed no growth we could not account for.

## The cores were at 600 MHz the whole time

The first JIT benchmark on the 3B+ ran at half the speed of the hosted emulator under Linux on the same chip: 77.2 s against 37.3 s on jitbench v1. Running the same suites side by side, every compute-bound item was 2.31-2.34x slower on bare metal. That was a constant ratio, and 1400/600 is 2.33.

The Pi firmware starts the ARM cores at `arm_freq_min`, which is 600 MHz on a 3B+. Raising them to the rated 1400 MHz is left to the operating system, which asks through the mailbox. Linux does this within a second of booting. Our kernel never asked, so every soak, battery and benchmark until then had run at 600 MHz.

[#691](https://github.com/infernode-os/infernode/pull/691) fixes it with one mailbox exchange at boot. The kernel reads the clock, reads the maximum, asks for it and reads back what was set, and the boot line prints all three. Nothing inside the system could have shown the slowdown, because a machine at 600 MHz looks like a slightly slow machine at 1400. The [porting lessons](https://github.com/infernode-os/infernode/blob/master/docs/BAREMETAL-PORTING-LESSONS.md) now say to measure against a known OS on the same silicon on day one.

At 1400 MHz, [docs/BENCHMARKS.md](https://github.com/infernode-os/infernode/blob/master/docs/BENCHMARKS.md) puts the bare-metal JIT within 4% of the hosted emulator on the same board on jitbench v1, and 33% faster on v2.

## Reals printed as garbage

On the bare-metal kernel, every Limbo `real` formatted as nonsense: `70.0` under `%g` came out as `4.15e-322`. Loading a map whose fixture writes positions with `%.6f` wedged the whole Dis VM until the board was reset. The hosted emulator had always been right.

The cause is in the AArch64 calling convention (AAPCS64). A `double` passed to a variadic function travels in a vector register, and `va_start` spills `v0`-`v7` for `va_arg` to find. Our `snprint` and `sprint` lived in `devcons.c`, which, like the rest of `os/port`, is built with `-mgeneral-regs-only`. Their `va_start` therefore spilled only `x0`-`x7`, and the float converter read the double from a save area nothing had written.

[#715](https://github.com/infernode-os/infernode/pull/715) moves the two functions into `printfp.c`, built with FP enabled and with `-mno-implicit-float`. FP has to be on so the vector registers are spilled. Implicit float has to be off because clang had otherwise copied the `va_list` through `q0`/`q1`, a write to FP state that is wrong if an interrupt arrives while a process has live FP registers. `tests/fltfmt_test.b` now runs inside the kernel image, with the JIT and without.

## A process table that filled

A GUI session with several apps open, followed by a theme switch, filled the kernel's process table, and every Limbo program then hung on "no procs". `conf.nproc` had been 100 since bring-up. Since March, each themed app has kept a listener blocked in a kernel read for as long as it is open, and a theme switch makes all of them reopen their colour files at once. [#716](https://github.com/infernode-os/infernode/pull/716) scales the table from RAM using upstream Inferno®'s `os/pc` formula, capped at 1000 slots, about 5 MB reserved. Kernel stacks are allocated only when a slot is first used.

Several of these fixes landed after the soak, so the kernel in 0.5.0 is not byte-identical to the one that ran for 48 hours. Each change ran on the board or under QEMU as its PR records. The changelog says so plainly.

## The TLS client did not authenticate servers

In February [we wrote](/blog/native-tls-13/) about building native TLS 1.3 in a day. We said that an assistant had made the volume possible and that test vectors and real servers had made it trustworthy. Test vectors made the cryptography trustworthy. They did not make the *authentication* trustworthy, because almost nothing in our tests presented a server that should have been refused and checked that it was. In fact our `tls` and `webclient` modules did not authenticate servers ([#693](https://github.com/infernode-os/infernode/pull/693)). Each of the following, on its own, let a network attacker impersonate any HTTPS server:

- X.509 chains did not have to reach a trust anchor. A self-signed certificate verified against itself, and an unknown issuer was accepted.
- TLS 1.3 did not require `Certificate` and `CertificateVerify`.
- TLS 1.2 skipped the `ServerKeyExchange` signature when it was absent or not RSA.
- The hostname check soft-failed when an extension did not parse.
- RSA PKCS#1 v1.5 signatures were verified by suffix match.

The client now builds an RFC 5280 path from the leaf to an anchor in `/lib/certs`, with backtracking. It enforces `basicConstraints`, `keyCertSign` and `pathLenConstraint`, checks validity and CRLs, and fails closed on any algorithm it does not support. Both TLS versions use one signature verifier with strict PKCS#1 v1.5 encoding, RSA-PSS and ECDSA on P-256 and P-384. The hostname check reads only `subjectAltName` and never soft-fails. The trust store was regenerated from the Mozilla root program, 121 roots, by `tools/update-certs.sh`.

Several extension decoders never advanced their loops or wrote through nil ADTs, so a certificate with CRL distribution points, which is common, crashed the client. Those are fixed too. The fix comes with the tests that were missing. `tests/x509_path_test.b` runs the path builder against a generated test PKI that includes self-signed, non-CA, wrong-key-usage and path-length-violating certificates, and `tests/tls_chain_live` checks real sites and badssl.com.

If you run an earlier release and use either module on an untrusted network, upgrade. The lesson is the one February should already have taught us: a test written from the same understanding as the code cannot find what that understanding missed. For a security property, the test has to be adversarial. It has to present the forged certificate and require that it be refused.

## What the soak taught us

Every problem above had been present for weeks or longer. The clock had been wrong since the first boot. The process table had been one theme switch away from full since March. The TLS client did not require a chain to reach an anchor. None of them needed cleverness to find. They needed us to run the real thing for longer and under more load than before, to compare it with a known reference (a second OS on the same board), and to ask what the system should *refuse* as well as what it should do. That is the escape room's approach, aimed at the kernel and the network stack instead of the namespace.

## Also in 0.5.0

The network that was slow at the start of the month now carries 160 Mbit/s in and 148 out on the 3B+'s USB-attached LAN7515, up from 7-32 inbound. The [porting lessons](https://github.com/infernode-os/infernode/blob/master/docs/BAREMETAL-PORTING-LESSONS.md) tell that story in full, from reading the chip's own counters to pause frames and selective acknowledgement. The release also brings a Limbo `int` that behaves as 32 bits on a 64-bit word in the interpreter and every JIT. The arm64 JIT now returns within a module inline, which makes recursive code 2-6x faster on the 3B+ (jitbench v2 went from 7,354 to 2,607 ms). The hosted arm64 emulator no longer leaks about 52 KB of compiled type code per command. `awk` keeps `$0` verbatim, and `break` and `continue` now work in its loops. The [changelog](https://github.com/infernode-os/infernode/blob/master/CHANGELOG.md) has the full list, including the known limitations. The Pi 4 and RISC-V ports are QEMU-only, and the release job does not build a card image; build one from the tag following the [bare-metal manual](https://github.com/infernode-os/infernode/blob/master/docs/BAREMETAL.md).
