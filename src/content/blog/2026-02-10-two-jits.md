Three weeks ago InferNode had one JIT that we believed worked (AMD64) and one that did not (ARM64). The ARM64 compiler could run `echo` and `cat` under `-c1`. It crashed with the frame-pointer register set to 1 as soon as a module needed more than 32 slots of immediate storage. Today both compilers pass the same 181 correctness tests on three machines, and we have numbers we are willing to publish. Why spend February on a JIT when the reason for InferNode is containing agents? The containment only matters if people can use the platform, and an interpreter that is an order of magnitude slower than it needs to be is a reason not to. The JIT was also a hard test of our working method: small team, AI coding assistants, and a codebase whose JITs predate 64-bit hardware. Most of the work turned out to be finding bugs rather than writing new code.

## First, a test suite

We could not judge either compiler without a test suite, so we wrote one first. [df517297](https://github.com/infernode-os/infernode/commit/df5172970cc68a17398fc80b8b7987d06b7ebdfe) added `jittest.b`, with 181 correctness checks across 20 categories (arithmetic, bitwise, shifts, comparisons, arrays, strings, lists, recursion, conversions, control flow, edge cases) for `int`, `big` and `byte`. It also added `jitbench2.b`, which has 30 benchmarks in 9 categories. Each test runs once under the interpreter (`-c0`) and once under the JIT (`-c1`), and the results must match.

The first real bug the suite found was not in a JIT. It was in the Limbo compiler. `globalBconst()` in `limbo/ecom.c` names each `big` constant after its hex value, formatted with `%.8lux` into a 32-byte buffer. On LP64 hosts `long` is 64 bits, so a negative half-word printed as 16 hex digits and was truncated. Every negative `big` constant got the same symbol name, and the deduplication pass merged them into one value. The fix masks to 32 bits explicitly. The bug appeared on AMD64 Linux first and on ARM64 macOS again in [70bdeae8](https://github.com/infernode-os/infernode/commit/70bdeae8a92dd40dd7181389b47af49c2a863b4b). Any LP64 build of the Limbo compiler has it, with or without a JIT.

## ARM64: fixing the old compiler

On 6 February we worked through the inherited ARM64 compiler one bug at a time:

- **Branch targets** ([0aa37ece](https://github.com/infernode-os/infernode/commit/0aa37eceb9a99a89c20551975419d113af483a84)). `(vlong)base + dst` cast too early, so word offsets were added as byte offsets. The same commit fixed a `schedcheck` skip that was one instruction short, and a `Type.destroy` path where `RET` returned to itself.
- **Inverted comparisons** ([84c26969](https://github.com/infernode-os/infernode/commit/84c2696978e1fb6e9b94f021eabd6cdf25751e47)). `CMP mid,src` instead of `CMP src,mid` reversed every non-symmetric branch on register operands.
- **Unsigned conditions on signed data** ([d7f46624](https://github.com/infernode-os/infernode/commit/d7f46624b3aeaa156416283f8e7b12ff097abaea)). The 32-bit ARM compiler compares a 64-bit `big` in two halves with LO/LS/HI/HS. ARM64 does one 64-bit `CMP` and needs LT/LE/GT/GE. This, together with an off-by-one in list length, was why `wc`, `sort`, `uniq` and `seq` hung.
- **CVTLW/CVTWL** ([47bdeba8](https://github.com/infernode-os/infernode/commit/47bdeba8544a1507d642aa320b4702d508bc5c18)). On ARM64 both WORD and `big` are 8 bytes, but the conversions used 32-bit loads and stores. The upper half of the slot kept stale `0xFFFFFFFF`, and `date` reported the year 1889.

macOS needed its own changes ([70bdeae8](https://github.com/infernode-os/infernode/commit/70bdeae8a92dd40dd7181389b47af49c2a863b4b)). Apple Silicon enforces W^X, so code buffers come from `mmap(MAP_JIT)` and are toggled with `pthread_jit_write_protect_np()`. `segflush()` still used a PowerPC-era call and had to use `sys_icache_invalidate()`. After all that, 181/181 tests passed on the Mac and the speedup over the interpreter was 1.19x. On the Jetson AGX Orin the same compiler averaged 3.65x ([c121d617](https://github.com/infernode-os/infernode/commit/c121d617)). We took those numbers out of the README the same day ([1b668a28](https://github.com/infernode-os/infernode/commit/1b668a28cfc9a71c02663f537c170ca31eede440)), because the code generator had not been tuned on any platform.

One more bug only showed up in real programs ([6fc95bb1](https://github.com/infernode-os/infernode/commit/6fc95bb19a3ddbd39cfa16775681c05843344ca0)). `patchex()` stored exception handler ranges as instruction counts, while `exception.c` computes byte offsets from `R.PC - m->prog`. They never matched, so every `raise` inside an `exception` block went through as unhandled. `jittest` had no exception tests. Xenith uses `raise` for ordinary control flow and hit the bug at once.

## ARM64: starting over

The inherited compiler left most of the work to the interpreter, and that is where the time went. On 8 February we replaced it ([518017ee](https://github.com/infernode-os/infernode/commit/518017ee245abb83da4eb95fb7e9b64f770bf3ce)). The new `comp-arm64.c` follows the structure of Inferno®'s 32-bit `comp-arm.c`, adapted for AArch64 with hardware floating point and divide, and keeps `&R`, `R.FP` and `R.MP` in callee-saved X20 to X22. It compiles every data operation inline. Channels, spawn, allocation and strings still go to C.

The rewrite found more bugs of the 64-bit kind. `Modlink.compiled` and `Type.size` are `int` fields, and loading them with a 64-bit load picked up the neighbouring field, so an uncompiled module looked compiled and the shell crashed returning from `Readdir`. Linux needed two small follow-ups, because `MAP_JIT` is Apple-only and the preamble needed an icache flush ([487144a7](https://github.com/infernode-os/infernode/commit/487144a7a32c5b7d95d3ff45c4d2a45f8980e386)). After that, one compiler serves both operating systems.

## AMD64: the compiler that "worked"

The AMD64 JIT ran simple programs, so we had assumed it was fine. `jittest` showed otherwise. [3336335d](https://github.com/infernode-os/infernode/commit/3336335db0c7c51cd450bd709159fc8d87e42100) fixed over a dozen code-generation errors:

- Linux had no allocator that put JIT code within 2 GB of the text segment, so `rel32` calls into C could not reach. The fix adds `jitmalloc()`.
- Array indexing was missing a `REX.X` prefix when R15 was the SIB index.
- Shifts used RBX as scratch, but RBX is the frame pointer.
- A `SHLD`/`SHRD` had its operands the wrong way round.
- A hard-coded backward jump was sized for 386 encodings, which have no REX bytes.

The next round ([b7fa8a65](https://github.com/infernode-os/infernode/commit/b7fa8a654f458ffc4a50b21e4aa5ecf63876f412), [59f5c9c0](https://github.com/infernode-os/infernode/commit/59f5c9c038923a3c1ab064a26e2df3844b7c1063), [d53cf4b2](https://github.com/infernode-os/infernode/commit/d53cf4b2bac01ebe49b9e890ffea1f6625bed19e)) followed the same pattern: constants that assumed instruction sizes. A bounds-check skip of 19 bytes assumed `con64()` emits 7 bytes, but for addresses above 4 GB it emits a 10-byte `MOVABS`. We replaced the hard-coded skips with backpatched labels. Bounds errors from compiled code are now catchable, because `genbounds()` saves `R.PC` before calling `bounds()`. One fix was not a size problem at all. `Math->FPcontrol()` can unmask x87 exceptions, so `MOVF` and `NEGF` now issue `FNINIT` before `FLD`.

## What the method taught us

Much of this code was written with AI coding assistants. Some of the AMD64 fixes came from an assistant working in a cloud session on a Linux machine, with the test suite as the measure of whether it was done. A compiler that runs `echo` is not yet a compiler that is correct, and a first benchmark number on untuned code is not a result, which is why we kept the early figures out of the README until the code generator had been worked on. What made fast iteration safe was a test oracle: 181 tests whose JIT results must equal the interpreter's. Anything we could not check against it, we checked by hand.

## Numbers

[docs/BENCHMARKS.md](https://github.com/infernode-os/infernode/blob/master/docs/BENCHMARKS.md) has the method and tables ([87bed0a4](https://github.com/infernode-os/infernode/commit/87bed0a4a236616ef26df52fb97fd903dec242f4)). All results are best-of-3 or best-of-4 with the machine idle, and JIT and interpreter results are checked against each other.

| Platform | v1 interp | v1 JIT | v1 speedup | v2 speedup |
|---|---|---|---|---|
| AMD64 Linux (Ryzen 7 H 255) | 21,255 ms | 1,500 ms | 14.2x | 5.7x |
| ARM64 macOS (Apple M4) | 16,697 ms | 1,735 ms | 9.6x | 2.6x |
| ARM64 Linux (Jetson AGX Orin) | 38,320 ms | 4,615 ms | 8.3x | 2.9x |

The v1 suite is mostly tight loops. v2 includes function calls, which gain the least (2.8x on AMD64). Every Dis call allocates a frame, checks the module pointer and validates types, and the frame layout is fixed by the Limbo compiler before the JIT sees it. Recursive Fibonacci is the worst case on every platform (2.6-3.6x).

We also ported the six v1 benchmarks to C, Go, Java and Python with matched parameters and 64-bit integers ([89dd20e9](https://github.com/infernode-os/infernode/commit/89dd20e911a31824256b6222c0ae184d199da4ce)). On the M4, best of three, JIT-compiled Limbo totals 1,330 ms. C at `-O2` takes 79 ms, Java 291 ms, Go 306 ms and C at `-O0` 661 ms. The interpreter takes 11,800 ms and CPython 15,055 ms. So Limbo under the JIT is about 2x slower than unoptimized C, and the JIT is about 9x faster than the interpreter. On the Jetson the gap to `-O0` C narrows to 1.4x.

That is the result we wanted. The Dis JIT is a single-pass translator with no optimizer. The VM is memory-to-memory, bounds-checks every index and keeps its garbage-collector invariants. We do not expect it to match Go or HotSpot. Its job is to make compute-bound Limbo practical, so that it does not need rewriting in C.

## What is left

Function calls are the obvious next target on both architectures, since they now account for most of the remaining distance. The 181 correctness tests have also moved into `tests/` as `jit_test.b` ([f903a1b2](https://github.com/infernode-os/infernode/commit/f903a1b2)). The test runner finds them automatically, so a code-generation regression shows up in the normal test run instead of waiting until someone runs `-c1` by hand.
