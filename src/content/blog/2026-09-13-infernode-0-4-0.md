[InferNode 0.4.0](https://github.com/infernode-os/infernode/releases/tag/v0.4.0) was tagged on 12 September. Most of the [changelog](https://github.com/infernode-os/infernode/blob/master/CHANGELOG.md) belongs to the line of work we started this project for: making an agent's namespace the boundary that contains it. This cycle that meant a `MREADONLY` mount flag that attenuates through rebinds and 9P exports, a finished port of the Fourth Edition pathname stack, and sealed agent trajectories. We'll come back to that work. This chapter is about a less glamorous change, because it says something about how this project is built and what that way of building costs.

## A ten-year gap, and how we work on it

When we forked Inferno®, we set out to test a second idea alongside the security one. The upstream system had been effectively still for about a decade. We wanted to know whether a small group, working closely with AI coding assistants, could close a gap that size. The work runs that way: many short branches in parallel, often in separate worktrees, each one small enough for a person to review and merge. The repository carries standing instructions for the assistants, a design-principles document, and skills for the compile loop and the test tiers. They exist because an assistant that doesn't know the toolchain's traps will walk into them as confidently as a new contributor would.

That way of working is fast, and it has one particular weakness: anything a person or an assistant produces by hand, outside the build, can survive unnoticed for a long time. In this tree, the clearest example was `dis/`.

## The second source tree

Inferno ships its runtime as Dis bytecode under `dis/`, and the 2006 upstream drop (still in our history as `46439007c`) tracked that directory in version control. We kept doing it, because a downloaded release should run without the user compiling anything. That reason is real, but it never required tracking the bytecode.

When we measured what tracking had cost ([#559](https://github.com/infernode-os/infernode/pull/559)), we found the committed bytecode had drifted from its source in every way it could:

- **Stale bytecode.** `dis/acme.dis` still looked for `/fonts/vera/Vera/unicode.14.font`. The source had used `/fonts/combined/unicode.sans.14.font` since 2026-03-06, so every release after that shipped an Acme that looked for fonts under their old names.
- **Code that did not compile.** A hardening change had removed a credential reader from the Git library so that agent tools could not load it. `appl/cmd/git/push.b` still called it, so the command had not compiled since 2026-07-02. Its old bytecode kept shipping, and nothing noticed.
- **Modules no build produced.** 45 `.dis` files had a Limbo source that no mkfile `TARG` named. They existed only because somebody had compiled them by hand once.
- **Binaries without sources.** A Veltro tool, `safeexec`, removed by a commit titled `chore(security)`, was still executable bytecode in the agent's tool directory of every release tarball. A second agent tool, `calendar.dis`, had no source anywhere in the history. And Tetris loaded `dis/lib/scoretable.dis` at runtime, a 2006 binary that nobody could rebuild.
- **Leaked paths.** `limbo` records the source path in the `.dis`. Several released modules carried the absolute paths of the worktrees they had been hand-compiled in, including the names of feature branches.

The last item is the clearest picture of the failure. Parallel branches had each compiled what they needed to wherever was convenient, and committed the result. The project instructions already warned about the "wrong-target trap": a hand-run `limbo -o` that writes to a path the runtime never loads, so a fix appears to have no effect. It had cost us several debugging sessions. But a warning is policy, and policy gets skipped under pressure. No CI or release job rebuilt `appl/` at all, so every release carried about 940 files that nothing had built from the tagged source.

## Recover, rebuild, untrack

We couldn't simply untrack the directory, because 25 tracked binaries had no source in the repository. We recovered sources from our own history where they existed. Seven of them (`popup`, `scoretable`, `cptree`, `items`, `wm/date`, `wm/sh` and `wm/task`) recompiled **byte-identical** to the shipped bytecode, which proves they are the exact sources those binaries came from. We removed what had no source, finished the deletions that had been left half done, and added the 45 missing targets to their mkfiles.

The next step depended on a property we measured rather than assumed. `limbo` output is deterministic and records paths relative to `$ROOT`. Before any of this work, 724 files in the tree already rebuilt byte-for-byte on Linux arm64 from bytecode committed on other hosts.

So `dis/` is now a build product, like `emu/*/o.emu`, which was never tracked. Only `*.dis` is ignored. The 51 hand-written Inferno sh scripts in those directories (`dis/lc`, `acme/dis/Clean`, `xenith/dis/Run` and the others) are real sources, and they stay tracked. A fresh clone builds its runtime in about 20 seconds:

```sh
export ROOT=$PWD
export PATH="$ROOT/$SYSHOST/$OBJTYPE/bin:$PATH"
for d in appl appl/mpeg appl/veltro tests; do (cd $d && mk install); done
```

`hooks/post-merge` runs the same loop after a `git pull`. All four directories are needed, because `appl/mpeg` and `appl/veltro` are not in `appl/mkfile`'s `DIRS`. That is the easiest step here to get wrong, so it is written down in every place a contributor or an assistant will look.

## A manifest instead of binaries

Untracking makes stale bytecode impossible, but it introduces a quieter failure. Drop a target from an mkfile and the module simply stops existing, and nothing reports it until something fails to load. That is exactly the state the 45 orphans had been in.

So we now track what the build must produce, as [`tools/dis-manifest.txt`](https://github.com/infernode-os/infernode/blob/master/tools/dis-manifest.txt). The 964 binaries became 964 lines of text, and a module appearing or disappearing is now a one-line diff in review. [`tools/verify-dis-build.sh`](https://github.com/infernode-os/infernode/blob/master/tools/verify-dis-build.sh) builds the tree and fails if anything on the list is missing. It runs on every PR and at all six release staging sites, which now build the runtime instead of copying a committed one. We checked that it fails, not just that it passes: an edit with no rebuild, a dropped `TARG`, a module compiled to the wrong path, a source that does not compile and a missing toolchain all exited non-zero.

## What we take from it

The lesson fits a project that argues for mechanism over policy. We had a rule, "rebuild properly, never hand-roll `-o`", and the tree broke it anyway. It broke it because the rule depended on everyone, human or assistant, remembering it on every branch. The fix was to make it impossible to commit the artefact and mechanical to check the build. When code is produced quickly, the defences have to be the kind that don't depend on anyone remembering.

0.4.0 also completes the move of our adversarial test harness, the escape room, out of the product tree into [its own repository](https://github.com/infernode-os/infernode-escape-room). A CI ring-fence now fails any release that contains harness material ([#585](https://github.com/infernode-os/infernode/pull/585)). The read-only mounts in this release ([#586](https://github.com/infernode-os/infernode/pull/586)) exist because our internal red-team campaign found a way to overwrite `sh.dis` through a view meant to be read-only. The harness pins the exact InferNode revision it attacks, so every finding is tied to a specific build.
